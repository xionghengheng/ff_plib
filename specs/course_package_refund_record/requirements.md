# 课包退费历史记录需求

## 简介

为课包退费及管理员课时归零操作增加独立历史记录，避免仅在课包表保存最后一次退费信息而丢失历史。本次范围为 ff_plib 中的 model、MySQL 建表 SQL 和 DAO 接口，不包含 HTTP handler 改造、线上退款或历史数据回填。

## 需求及验收标准（已确认）

### 需求 1：独立保存历史

用户故事：作为管理员，我希望查看每一次退费或课时归零的操作记录。

1. 当业务层新增退费历史时，系统应新增独立记录，不覆盖该用户或课包已有的记录。
2. 当保存记录时，系统应支持记录主键 ID、用户 UID、课包 ID、退费/清零课时数、退款金额（整数元）、退费时间（Unix 秒）、操作人、备注、创建时间（Unix 秒）。
3. 当课时归零但未发生线下退款时，系统应允许退款金额为 0；历史记录不代表发起或完成线上退款。
4. 当业务层传入记录时，DAO 应仅负责持久化；字段有效性、操作权限、课包归属和业务状态判断由上层负责。

### 需求 2：查询历史

用户故事：作为管理员，我希望按退费时间分页查看全部记录。

1. 当查询历史时，系统应提供全量列表查询，不提供按 UID 或课包 ID 查询的接口。
2. 当列表分页时，系统应按退费时间 refund_ts 降序返回，同一时间按 ID 降序；首页传 (lastRefundTs, lastID) = (0, 0)，后续传上一页最后一条的 RefundTs、ID，不使用 OFFSET。
3. 当访问数据库时，新增应沿用 GORM Create，查询应使用带参数的 Raw SQL。
4. 当创建表时，系统应提供主键及与退费时间游标查询匹配的索引，不对 UID 或课包 ID 设置唯一约束。

### 需求 3：集成边界

1. 当接入实际退费/归零流程时，业务层应保证课包更新和历史新增的一致性，避免只完成其中一步；本次不自动修改现有课包更新接口。
2. 当提供历史接口时，系统应仅提供新增和查询，不提供覆盖历史的更新或删除接口。
3. 当交付时，应提供建表 SQL 和相关包编译检查结果，不直接操作数据库。
